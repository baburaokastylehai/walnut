# Pull role lenses

Role lenses change emphasis, not truth.

All roles should understand the core problem, current solution direction, project status, and meaningful project-wide changes.

## Designer

Prioritize:
- user/problem context;
- workflows and states;
- information hierarchy;
- interaction changes;
- configuration choices visible in UI;
- edge cases;
- terminology;
- unresolved behavior that blocks design;
- impacts to existing Arena experiences.

Translate backend/technical decisions only far enough to explain their user-experience consequence.

## Developers & QA

Prioritize:
- exact behavioral requirements;
- state transitions;
- conditions/configuration;
- compatibility/migration;
- data/model implications when confirmed;
- dependencies and cross-impact;
- edge cases;
- error/validation behavior;
- acceptance-relevant detail;
- unresolved questions that can change implementation or testing.

For QA, emphasize observable behavior and scenario boundaries.

Do not invent implementation architecture from product requirements.

## Technical Writer

Prioritize:
- user-visible behavior changes;
- terminology and renamed concepts;
- workflow changes;
- configuration/admin behavior;
- prerequisites and limitations;
- what is new vs changed vs removed;
- decisions that affect help content;
- unresolved items that make documentation premature.

Preserve Arena vocabulary and explain old → new terminology when relevant.

## PM

Prioritize:
- problem and intended outcome;
- decisions and firmness;
- requirements;
- unresolved questions and owners;
- proposals under consideration;
- research/findings;
- cross-team/product dependencies;
- scope changes;
- project phase and validation.

PM does not need every implementation detail unless it affects product behavior, risk, sequencing, or scope.

## Other roles

Infer the closest useful lens from the person's own description.

Do not force them into one of the four named groups.

## Relevance levels

### for you
Directly affects the role's current work or understanding.

### needs attention
The source indicates their role/person/team owns or must contribute to something, or a confirmed dependency clearly blocks their work.

### project visibility
Meaningful project movement that is not directly actionable for the role.

Keep project visibility concise, but do not omit it.
