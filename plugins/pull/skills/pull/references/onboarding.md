# Pull onboarding

First use should feel like joining the project, not configuring software.

## Ask one useful question

When there is no saved role, ask:

> before i catch you up — what are you working on this project as? design, dev/QA, technical writing, PM, or something else?

Natural free-text answers are valid.

Do not ask for information that can already be inferred safely from an explicit answer.

## Role persistence

Save the answer locally in the pull profile.

A person's role is a relevance lens, not an authorization boundary.

The role controls:
- which details get more explanation;
- which updates appear under "for you";
- which implications Walnut calls out.

It does not control which confirmed project facts the person is allowed to know.

## First briefing

After role selection, read the project brain and explain the project from the beginning.

The person should leave the first pull able to answer:
- what problem are we solving?
- what are we proposing/building?
- why does it work this way?
- where are we right now?
- what part of this should I care about?
- what is still unresolved?

Do not make them reconstruct that story from categorized records.
