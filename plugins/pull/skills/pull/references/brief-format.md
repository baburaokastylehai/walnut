# Pull briefing format

The response should optimize for understanding, not database completeness.

## First pull

Use this shape when useful:

### what we're solving
A short, natural explanation of the problem in Arena context.

### where we're going
The current/proposed solution, described as a coherent product direction.

### where it stands
What is settled, what is still being worked through, and the current phase.

### what matters for you
Role-specific context with enough detail to start useful work.

### still open
Only unresolved items that meaningfully affect the project or this role.

Do not mechanically emit a heading when there is nothing useful under it.

## Recurring pull

Start with the result.

If there are updates:

### changed since your last pull
For each meaningful update:
- what changed;
- why it matters;
- role relevance: for you / needs attention / project visibility;
- stable ID only when useful for traceability.

Put role-relevant changes first.

Then include a compact project-visibility section for important changes outside their domain.

If nothing changed:

> you're caught up. nothing meaningful changed since your last pull.

Do not repeat the full project overview unless:
- it materially changed; or
- the person asks for a refresh/full context.

## Detail

A designer may need a workflow explanation.

A developer may need conditions and edge cases.

A technical writer may need exact terminology and user-visible behavior.

"Role-aware" means changing the explanation depth and emphasis, not merely adding a role label to the same summary.
